# 遠端整合與衝突

## 範圍與證據

- 呼叫流程需要整合本地與遠端變更時，使用此指引。同一範圍沿用既有授權；整合不代表授權未要求的 push 或發布。遵循明確指定的整合策略；未指定時，優先採保留雙方歷史的 merge。嚴禁丟棄無關工作、改寫已發布歷史，或以 force-push 略過分歧。
- 更新所選遠端資訊，確認目標分支、共同祖先、本地 SHA 與遠端 SHA。分別對照共同祖先檢視雙方 diff，閱讀受影響的程式與需求，以具體輸入／輸出說明各自預期行為。依行為與交互作用評估，不能只看衝突行數或檔案數；Git 無衝突地合併不代表功能相容。

## 決策規則

1. 雙方在同一條件下要求互斥行為時，必須在提交選定解法、打 tag 或發布前停止，交由使用者決策。嚴禁靜默選邊、丟棄功能，或自行增加設定開關迴避決策。
2. 雙方意圖看來可相容，但保留兩者需要推理共享邏輯、介面、狀態、順序、錯誤或資料轉換時，先準備可供審查的整合候選結果，接受解法或 push／打 tag 前必須呼叫獨立 reviewer。沒有文字衝突的複雜交互作用也適用。無法證明屬於簡單整合時，採此審查流程。
3. 只有雙方意圖與組合方式明確、不需取捨行為，且適當檢查支持結果時，才自主解決，例如在文件清單加入互不相依、原意不變的項目。

## 審查與後續處理

1. 提供 reviewer 共同祖先、雙方 SHA 與 diff、各自需求及預期行為、合併方案與驗證結果。使用 context 指定或可用的獨立 reviewer；自行重讀不能取代此要求。必要審查無法執行時，停止並回報阻礙。
2. 對照實際修改核實 findings，並討論分歧。審查必須檢查雙方預期行為是否保留及其交互作用。以針對性檢查或測試涵蓋雙方與必要的組合案例；只有移除衝突標記或通過既有測試，證據仍不足。必須說明剩餘不確定性，不能宣稱完整等價。
3. 審查與調查後，仍無法確認雙方意圖均被保留，或確認存在不相容時，在提交選定解法、打 tag 或發布前停止，交由使用者決策。保留工作供檢視。回報雙方各自要求、具體衝突或尚未驗證的案例、不能自主決定的原因、選項與行為影響，以及目前整合狀態。
4. 適用檢查通過，且必要審查沒有未解決的實質問題後，只繼續已授權流程。任一方變更時，重新評估整合結果；解法有實質變更時，必須重新審查。發布流程則交回最終內容與版號驗證，再打 tag 或發布。

## 範例

- 簡單：雙方在文件清單新增互不相依的支援選項。保留兩項，對照實作確認原意後繼續，無須強制呼叫 reviewer。
- 複雜：一方修改重試上限，另一方修改可重試的錯誤種類。保留兩項要求，檢查設定上限下的暫時與永久錯誤；即使 Git 自動合併成功，也必須審查。
- 不相容：同一筆過期憑證，一方要求回傳 `401`，另一方要求降為訪客並回傳 `200`。停止並列出選項；agent 與 reviewer 均不能代替使用者選擇產品行為。
