# Misty Release

## 選擇發布流程

1. 檢查使用者指示、對話 context、儲存庫規則、發布文件、適用的 skill 與發布自動化，找出本次發布應遵循的流程。選擇流程前，先讀取適用的發布 skill。
2. 專案指引明確採用此 skill 的預設流程，且只補充專案輸入或動作時，讀取[預設發布流程](references/default-release_ch.md)作為採用的基礎流程，在對應步驟套用補充。此明確委派不代表選用另一套獨立專案流程；嚴禁轉回委派的轉接入口，或以其版本／同步要求為由略過已採用的基礎流程。此採用所涵蓋的決策，以採用流程為準，優先於從歷史推得的慣例。使用者明確限制與明訂的專案補充優先於基礎流程；受影響步驟前先解決衝突。
3. 否則，已有適用流程時，依該流程執行。嚴禁載入或套用預設流程的分支、note 保留數、commit 語言或 tag 模型。若該流程留下必要決策未定，只詢問該項；細節缺漏不代表授權套用整套預設流程。
4. 否則，沒有適用發布流程時，讀取並使用[預設發布流程](references/default-release_ch.md)。使用者明確限制仍然有效；執行受影響步驟前，先解決衝突。

## 基本詢問與授權

1. 確認發布單位、來源候選版本、適用的前一版、版號或選版規則，以及要求的結果：僅撰寫 notes、本地準備或對外發布。沿用已有答案與授權；只詢問無法從現有 context 確認的資訊。
2. 修改發布檔或整合前，展示目前分支、預定目標、發布範圍與對外發布效果。同一來源、目標與範圍尚無明確授權時，詢問是否執行。嚴禁將本地準備的授權視為 push 或對外發布的授權。
3. 只要求 notes 時，回傳草稿，不改動 Git 狀態。依選定流程驗證結果後才能回報完成；區分已準備內容、已發布結果及待完成檢查。

## 流程選擇範例

- Commit 與 release 指引分別判定：專案的 commit message 慣例本身不等於發布流程；發布流程本身也不等於一般 commit 慣例。
- 專案發布 skill 使用維護分支、保留全部 notes，並透過 CI 發布：依該 skill 執行，不載入預設流程。
- Local 入口明確採用 `misty-release`，並指定版號檔及套件同步命令：使用已採用的預設流程及這些專案動作，不能轉回 local 入口。
- 使用者指定版號，但沒有發布流程：沿用該版號套用預設流程，只詢問尚未確定的發布決策或授權。
- 專案流程定義了 tag 方式，但必要的 note 位置未定：詢問該位置，不能靜默套用預設路徑或保留政策。
