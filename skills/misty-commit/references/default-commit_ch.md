# 預設提交指引

- 入口檔因專案明確採用此預設流程，或沒有適用 commit 指引而選用時，才讀取此參考文件。使用者明確限制與專案補充優先。

## 提交邊界

1. 清點範圍內的實際修改，包括已暫存、未暫存與未追蹤內容，依任務情境辨識不同意圖。嚴禁只因無關修改存在於工作樹或暫存區，就將其納入提交。
2. 每個 commit 必須只有一項連貫意圖；不同意圖必須分開提交，即使位於同一檔案。同一意圖的實作、測試與文件應一起提交。
3. 執行適合該變更的檢查，只暫存選定內容，提交前核對最終暫存 diff、意圖與訊息。既有暫存修改妨礙限定範圍提交時，先釐清處理方式，不能靜默納入或取消其暫存。

## 訊息規範

- 使用 Conventional Commits 格式 `type(scope): summary`；沒有合適元件名稱時省略 scope。Subject、body 與 footer 的解釋文字必須使用繁體中文；技術識別字、type/scope 與標準 trailer 保留必要原文。
- 依交付變更選擇 type：新增能力用 `feat`，修正用 `fix`，不改變行為的重構用 `refactor`，文件用 `docs`，測試用 `test`，其他對應維護工作用 `chore`、`build` 或 `ci`。Commit type 本身不能決定升版幅度。
- Subject 必須描述高階意圖與具體成果：哪項能力、行為或設計責任改變，以及其意義。嚴禁逐項敘述檔案編輯、函式修改，或只寫「更新」「改善」等模糊活動；嚴禁宣稱無證據的效益。
- 需要補充動機、觸發條件、根因、取捨或遷移方式時才加入 body。不相容變更無論 type 為何，都必須以 `!` 或 `BREAKING CHANGE:` 標示，並說明受影響行為與必要遷移方式，讓後續發布能區分相容修復、新能力與不相容變更。

## Amend、Push 與發布

- 實際提交時，若已確認最新 commit 尚未推送，且新變更延續同一意圖，應詢問是否 amend 併入該 commit；取得使用者同意後才能 amend。若推送狀態不明、已推送或意圖不同，則建立新 commit。已有明確 amend 授權時，在其範圍內沿用，不重問。
- 完成本次要求的 commit 或 amend 後，詢問是否 push；使用者已授權或拒絕時，沿用既有指示。仍在發布流程中時，交回該流程完成發布準備，並一併取得缺少的對外發布授權；不能獨立 push 或重複詢問該流程已確認的授權。
- 遠端前進導致已授權的 push 前需要整合時，讀取[遠端整合與衝突](remote-integration_ch.md)。即使 Git 合併沒有衝突標記，也必須依該文件評估行為影響。
- 回報建立的 commit SHA 與交付意圖。後續發布可結合完整訊息與實際 diff，整理成果導向 notes 及推薦版號；嚴禁讓一般 commit 自行建立 tag 或啟動發布。

## 範例

- 修復既有重試在暫時斷線時過早中止：使用 `fix(upload): 修正暫時斷線時重試過早中止`，避免 `fix(upload): 修改重試次數與錯誤處理`。
- 新增相容的上傳結果報表 CSV 匯出能力：使用 `feat(export): 支援將上傳結果報表匯出為 CSV`。
- 移除既有支援的旗標：使用 `feat(upload)!: 統一上傳重試參數`，body 說明移除 `--retry-count` 與改用 `--retries` 的遷移方式。
- 不改變行為，將到期管理責任移入快取：使用 `refactor(cache): 集中快取到期管理責任`，避免 `refactor(cache): 搬移函式並調整呼叫點`。
- 上傳重試與發票捨入修正是兩個意圖，即使修改同一檔案，也應分成兩個 commit。上傳重試的測試與文件則與該變更一起提交。
- 專案沒有 commit 或 release 指引時，先將修復與新能力分開提交。使用者要求發布後，`misty-release` 對照 default branch 上次發布 tag，核對完整訊息與 diff、推薦最高影響等級的升版，並準備 release note。該 note 與版號修改形成發布準備 commit，例如 `chore(release): 發布 v2.5.0`；此發布紀錄 commit 本身不列為使用者可見的 release-note 項目。
