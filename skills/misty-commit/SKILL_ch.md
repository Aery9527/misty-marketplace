# Misty Commit

## 提交邊界

1. 清點範圍內的實際修改，包括已暫存、未暫存與未追蹤內容，依任務情境辨識不同意圖。
2. 每個 commit 必須只有一項連貫意圖；不同意圖必須分開提交，即使位於同一檔案。同一意圖的實作、測試與文件應一起提交。
3. 每則訊息必須對應該 commit 選定的變更；實際提交前，再核對最終暫存內容、意圖與訊息是否一致。意圖不明時先釐清，嚴禁編造。

## 訊息規範

- Subject、body 與 footer 的解釋文字必須使用繁體中文；技術識別字、type/scope 與標準 trailer 保留必要原文。
- 遵循儲存庫的訊息格式；未指定時使用 `type(scope): summary`。依意圖選擇 type 與可選的 scope。
- Subject 必須描述高階意圖與具體成果：哪項能力、行為或設計責任改變，以及其意義。嚴禁逐項敘述檔案編輯、函式修改，或只寫「更新」「改善」等模糊活動；嚴禁宣稱無證據的效益。
- 需要補充動機、觸發條件、根因、取捨或遷移方式時才加入 body。使用 Conventional Commits 時，以 `!` 或 `BREAKING CHANGE:` 標示不相容變更，說明影響與遷移方式。

## Amend 與 Push

- 實際提交時，若已確認最新 commit 尚未推送，且新變更延續同一意圖，應詢問是否 amend 併入該 commit；取得使用者同意後才能 amend。若推送狀態不明、已推送或意圖不同，則建立新 commit。已有明確 amend 授權時，在其範圍內沿用，不重問。
- 完成本次要求的 commit 或 amend 後，詢問是否 push。若使用者已明確授權或拒絕推送本次提交，則依既有指示執行，不重複詢問。

## 範例

- 為暫時斷線加入重試：使用 `fix(upload): 避免暫時斷線造成上傳失敗`，避免 `fix(upload): 修改重試次數與錯誤處理`。
- 不改變行為，將到期管理責任移入快取：使用 `refactor(cache): 集中快取到期管理責任`，避免 `refactor(cache): 搬移函式並調整呼叫點`。
- 上傳重試與發票捨入修正是兩個意圖，即使修改同一檔案，也應分成兩個 commit。上傳重試的測試與文件則與該變更一起提交。
