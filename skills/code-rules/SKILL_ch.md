# Code Rules

- 以下說明與範例皆使用 Golang，必須依目標語言調整相同的慣例與語法。
- 規範的優先順序必須為：專案明文規範、現有專案程式碼中一致的慣例、語言慣例，最後才是以下規則。
- 主編號清單的每個項目必須以簡短標題開頭，標題後接冒號「：」，再寫說明。子項目可直接寫說明。
- 以 *章節:編號[+編號…]* 表示參照的項目。同章多個項目的編號以 `+` 串接。
    - *程式碼原則:4.1* 表示該章第 4 項的第 1 個子項目。
    - *程式碼原則:2+3* 表示該章第 2 與第 3 項。
    - 同個章節內的引用可省略章節。例如在程式碼原則章節，*程式碼原則:4.1* 可簡寫為 *4.1*。
    - 子項目引用自身主項目時不需要這個寫法，保持自然語言描述即可。

## 變更原則

1. 確認現有契約：改變行為前，必須先讀直接 caller、覆蓋受影響行為的測試與所在模組。

## 程式碼原則

1. 巢狀限制：控制結構最多 2 層，`if`、迴圈、`switch` 與例外處理區塊各算一層，例如 Go 的 `if`、`for`、`switch`、`select`。
    1. `if a { for _, x := range xs { use(x) } }` 允許，在其中再加第三層結構，例如 `if b`，則禁止。
    2. `if` / `else if` / `else` 串接算一層。
2. func 內容：同一個目的的一組步驟，必須抽出為 func，以命名表達該組目的；只有當命名能明確包含多行程式碼組合起來的含意時才抽出。
3. func 聚攏：若多個 func 的涵義可以進一步以內聚力更高、含意邊界更清晰的名稱匯集起來，就該建立 struct 或模組收攏這些具有相同 scope 的 func，例如 Go 的 package 或作為 func receiver 的 struct。
4. func 參數：非建構子的邏輯 func 參數最多 3 個，在可預見的未來必須維持簽名的穩定性。
    1. 超過 3 個參數時，必須先審視 `func` 的責任。若多項計算各有獨立意義且可單獨使用，必須依責任拆成不同的 `func`。參數屬於同一 scope 且應一起傳遞時，才以 `struct` 包裝。
    2. 若 func 在可預見的未來會有持續擴充參數的可能，則必須使用專用的 struct 包裝相同 scope 的參數，避免簽名破壞性更新，並且必須註明清楚每個參數是否必填或預設值是什麼。
    3. 執行脈絡與接收物件不計入上限，例如 Go 的 `context.Context` 與 func 的 receiver。
    4. 受框架或函式庫約束的 func 簽名不受參數上限限制，仍必須遵守外部契約。
5. func 行數：維持 50 行內，行數從 func 簽名的第一行算到結尾的那一行，包含空白行與註解；若必定超過則依 *2+3* 調整。若內容類似「多個 `if-else` 串接」、「逐一判斷多種錯誤」這種機械式操作，則意味著結構設計問題，必須以更高的視角進行調整。分支會持續增加且各有獨立邏輯時，見 *架構原則:5*。
6. 相同涵義常數：若有許多地方的常數都代表同一個含意，必須使用一個常數來指定或串接，以明確的程式碼代表它們的關聯。
    1. 例如 URL 路徑前綴，一個 scope 的 API 端點的前綴定義一個常數串接；嚴禁以字面值重複寫出前綴，讓更換前綴時只需改一個常數，也更方便追蹤。
    2. 測試必須獨立指定請求與預期結果中的待驗證值，嚴禁引用正式程式中定義該值的常數，讓常數寫錯時測試會失敗。多個測試指定同一含意的值時，必須使用測試專用常數。只在一個測試指定的值寫成字面值。這是唯一的例外。
7. 宣告命名：以 `type` 宣告的名稱必須表達資料的含意或職責。後綴必須補充具體含意，例如 `ShippingConfig` 表示配送設定。嚴禁使用未增加含意的後綴，例如無法與 `Member` 區分的 `MemberData`。
8. 呼叫順序：若 func 之間有呼叫順序，例如先 `index.Load()` 才能 `index.Find(key)`，必須以註解說明，見 *註解原則:3*。
    1. 也可調整結構，以程式結構強制使用者按順序執行。例如先以 `connection, err := gateway.Connect()` 取得連線，才能呼叫 `connection.Send(message)`，如此便可以省略註解。
    2. 必須有明確的理由，才能設計成有呼叫順序的限制；例如 `Connect()` 必須先執行一次才能呼叫其他 func，但它的成本可能很高，所以由呼叫端決定在建立時呼叫，還是延後到第一次使用時才呼叫。
    3. 釋放資源的 func 不在此限。struct 必須遵循語言釋放資源的慣例，由持有它的程式釋放。例如 Go 的 struct 實作 `io.Closer`，只在一個 func 內使用該物件時，以 `defer` 關閉。
9. override：override 已有實作的 func 時，行為必須與被 override 的 func 不同。沒有不同時嚴禁 override。在 Go，本項適用於外層 struct 宣告的 func 與嵌入欄位提升的 func 同名的情況。
10. 執行緒安全：具名宣告的實例預設為非執行緒安全。實例具備執行緒安全保證時，必須遵守 *註解原則:4*。這裡的執行緒是指語言並行執行的單位，例如 Go 的 goroutine。
    1. 必須一起完成的步驟須由單一 func 提供，並在同一次同步內完成，若步驟中有需要呼叫端自定義了邏輯時必須提供 callback 機制一起在同步內完成。
    2. interface 的執行緒安全契約依 *註解原則:4.3* 說明。interface 要求執行緒安全時，每個實作都必須符合。
    3. 有 receiver 的 func 必須提供與其 receiver 相同的執行緒安全保證。若同一具名宣告同時有執行緒安全與非執行緒安全的 func，通常意味著責任不清，必須重新審視設計是否需要調整。

## 錯誤原則

1. 禁止隱藏失敗：嚴禁吞掉錯誤、回傳假成功，或在契約未定義 fallback 時靜默降級。
2. 處理位置：只在能恢復、能轉換為邊界契約、或能決定最終結果的地方處理錯誤；其他地方必須讓錯誤傳遞給上層，需要附加上下文時，傳遞保留原本錯誤的新錯誤，例如 Go 的 `fmt.Errorf("load orders: %w", err)`。
3. 單次記錄：同一個失敗只 log 一次，由決定最終結果的那一層負責。嚴禁每層都 log 又往上傳。

## 架構原則

1. 組合代替繼承：多個 struct 有相同 scope 的一組欄位或行為時，必須以獨立的 struct 組合而非繼承，透過 interface 定義共同契約。
    1. 例如 API 的 request/response 通常會利用父類來收斂相同的欄位，但相同欄位可能還是有 scope 區分，透過組合與 interface 定義可以合適的區分 scope 使 API 的 request/response 擁有必要且沒有多餘的內容。
    2. 必要的繼承不在此限，例如目標語言的例外機制或 lib 要求的繼承。lib 的情況可以考慮使用 adapter 來轉接組合。
2. 模組邊界：每個模組必須自行定義對外邊界的 input/output 宣告，例如查詢可接收以 `type MemberID string` 宣告的 `MemberID`。模組外部只能透過該邊界使用模組，嚴禁相依模組的內部實作。
    1. 業務邏輯不相依溝通協定。HTTP adapter 必須把 `*http.Request` 轉成模組邊界的 input，並將模組回傳的 output 寫入 `http.ResponseWriter`。框架綁定的請求參數也必須先轉成模組邊界的 input 再呼叫模組，該進入點嚴禁包含業務邏輯。
    2. 邊界傳入的參數一律進行驗證，在同一模組信任範圍內，嚴禁逐層機械地重複相同驗證。
    3. 驗證只拒絕契約不允許的值；`0`、`false` 與空字串並非一律無效。
    4. 契約允許省略的值必須寫明預設值。若省略與明確傳入零值，例如 `0`、`false` 或空字串，有不同含意，input 宣告必須能區分兩者，例如 Go 的欄位宣告為 `*int` 而非 `int`，以 `nil` 表示省略。
    5. 新增必填輸入（個別參數或 input 的欄位），或將既有輸入改為必填前，必須檢查資料的建立與載入來源，找出會缺值的來源，並確認邊界的驗證能識別缺值。可控制的來源在同次變更更新。無法同步更新的來源，保留相容入口，或明述不相容變更與遷移方式。例如 `MemberRegistration` 新增必填欄位 `Locale` 時，已儲存的舊資料與其他建立會員的流程沒有這個值。
    6. 重組內部實作時，必須維持對外操作的呼叫方式與呼叫端責任，既有輸入含意、結果與錯誤也必須維持。
3. 功能解耦：跨模組邊界的功能，或實作尚未定案、需要替換的功能，必須透過 interface 隔離提供實作，並確立好該 interface 的所有 input/output 是否足夠獨立，僅相依必要的其他模組元件。模組間若邊界無關連則透過 adapter 耦合，避免依賴。
4. 禁止循環相依：模組之間的相依嚴禁直接或間接形成循環。循環相依意味著模組功能模糊，必定能再抽出更底層的邏輯將循環相依拆開。
5. 邏輯分支：已知需求或既有擴充點顯示 `if-else`/`switch` 的分支會持續增加，且每個分支對應一組獨立邏輯時，必須讓選擇分支的責任與處理邏輯解耦，使其可以獨立發展；嚴禁只因分支增加就把 `switch` 換成 `map` 或 Strategy。
    1. 封閉集合：選擇分支的模組擁有全部分支，新增分支時允許修改選擇者。保留 `switch`，每個分支呼叫一個具名的 func。
    2. 開放集合：分支由其他模組或在執行時提供，新增分支時不得修改選擇者。以唯一的 key 選擇分支時，必須使用分派表：由外部註冊 key 與處理者的對應，選擇者只相依共同的 interface。
    3. Strategy Pattern 是處理邏輯的封裝方式，可與 *5.1* 或 *5.2* 的選擇方式並用：各分支有各自的設定與邏輯，且需要以共同的契約替換時使用；固定且簡單的分支嚴禁只為套用模式而建立 Strategy。
6. 資料與邏輯分開：只用來承載資料的 struct，例如 DTO、API 的 request/response，只宣告欄位與存取欄位的 func，嚴禁帶有任何邏輯。邏輯必須放在使用這些資料的 func 或 struct。邏輯是指依欄位值做判斷、計算或轉換，或讀取外部狀態的程式。
    1. 例如判斷查詢點是否位於搜尋範圍內，必須寫成 func `func Contains(bounds Bounds, x, y float64) bool`，嚴禁以 `Bounds` 為 receiver 宣告 `func (bounds Bounds) Contains(x, y float64) bool`。
    2. 建構時的驗證也屬於邏輯，嚴禁寫在資料 struct 內。資料由接收它的邊界驗證，見 *2*。
    3. 預設值的替換與格式的正規化，例如去除前後空白，也屬於邏輯，嚴禁寫在資料 struct 內。契約定義的預設值由定義該契約的邊界替換。正規化可以由邊界處理，也可以由呼叫端在傳入前處理，例如同一筆資料要傳給多個模組時只處理一次。
    4. 由邊界替換預設值或正規化，且邊界是 interface 並有多個實作時，必須寫在各實作共用的一個 func，嚴禁每個實作各寫一份；例如 `MemberSearch` 的每個實作都呼叫 `ApplyMemberQueryDefaults(query)`。
    5. 為了讓來源集合之後的修改不影響資料而複製集合不屬於邏輯，例如 Go 在建立該值的 func 以 `slices.Clone` 複製 slice。
    6. 資料與邏輯分開的規則也適用於列舉。每個值可以有與值一起宣告的固定屬性，並提供只查出並回傳該屬性的 func，例如 `func (channel Channel) MaxLength() int` 由以常數為索引的表回傳長度上限。依屬性或傳入的參數做判斷或計算的 func 屬於邏輯，嚴禁以列舉值作為 receiver，例如 `func (channel Channel) Accepts(text string) bool`。由固定屬性找出對應值的 func 不屬於邏輯，例如 `func ParseChannel(code string) (Channel, error)`。
    7. 目標語言支援純資料專用宣告時，資料 struct 的對應宣告必須採用該形式，且欄位在建構後不可改變。只有語言版本或函式庫不支援該形式時，才改用其他宣告方式。帶有邏輯的 struct 嚴禁使用純資料專用宣告，例如 Strategy 的實作。

## 註解原則

1. 高階意圖：僅描述高階用途、資料含意、契約、限制與取捨。嚴禁逐步描述實作。
2. 清單結構：註解有兩個以上獨立要點時，必須用清單結構，而非文章式的描述。
3. 用途註解：每個以 `type` 宣告的名稱、func 與 field 都必須有精簡註解，提供用途或含意的高階概覽。
    1. 以 `type` 宣告的名稱，其註解必須說明職責與範圍。優先描述所負責的功能。不負責的功能由流程或模組邊界表達。
    2. field 的註解必須說明資料含意，若有固定格式則必須提供範例。
    3. func 的任一參數有名稱與宣告看不出的含意、格式、單位、可否不提供（例如 Go 的 `nil`），或省略時的預設值時，必須依語言的文件慣例在 func 的註解說明每一個參數。在 Go，把每個參數寫成 doc comment 內的清單項目。若有固定格式則必須提供範例。若上述資訊都能由各參數的名稱與宣告看出，則省略全部的參數說明。
    4. 實作 interface 要求的 func 或抽象 func 時，契約已由原宣告說明，註解只寫這個實作特有的行為與限制。若無特有行為與限制，宣告已標示實作關係時可省略註解。否則寫一行指出實作的契約，例如 Go 以 `// Send 實作 Sender。` 說明隱含的實作關係。
    5. override 已有實作的 func 時，註解必須說明它與被 override 的 func 不同的行為，見 *程式碼原則:9*。
    6. func 若有簽名與相關宣告無法表達的前置條件必須明確列出，例如呼叫端必須已完成的驗證、跨模組契約，以及呼叫順序（見 *程式碼原則:8*）。無此類限制時省略這些補充項目。呼叫順序必須註明必須先呼叫哪一個 func，以及未依順序呼叫時回報的錯誤。只能呼叫一次的 func 必須註明這個限制，以及重複呼叫時的行為。嚴禁只為重述呼叫關係而列出 caller 或 callee。
4. 執行緒安全：具名宣告的註解沒有說明執行緒安全時，同一個實例嚴禁由多個執行緒同時使用。具備執行緒安全保證時，必須在宣告的註解寫明，用語依語言的慣例，例如 Go 的「可由多個 goroutine 同時使用」。
    1. 若實例持有的資料在建構後不會改變，該實例就是執行緒安全，可省略說明。以固定常數表示的列舉亦同。是否會改變必須依實際的程式碼判斷，嚴禁只看宣告，例如 Go 以值傳遞 struct 時會複製，但複本的 slice field 仍與原本的值共用元素。
    2. 其他具名宣告的實例若設計為執行緒安全，必須寫明，例如 Go 以 `sync.Map` 保存資料、由多個 goroutine 共用的 cache，註解寫「可由多個 goroutine 同時使用」。
    3. interface 定義的邏輯必須是執行緒安全時，interface 註解必須寫明，例如「實作必須可由多個 goroutine 同時使用」；實作可以有執行緒安全與非執行緒安全兩種時也必須寫明，例如「實作是否可由多個 goroutine 同時使用，依各實作的註解」。不屬於這兩種情況的 interface 不需要寫；沒有寫明時，嚴禁假設它的實作是執行緒安全。
    4. 同步會讓呼叫端等待時，註解必須寫明哪些 func 會互相等待，例如「可由多個 goroutine 同時使用。`Reload` 執行期間，其他 func 的呼叫會等到它結束」。等待可能很久時，還必須寫明原因，例如持有鎖期間讀取檔案。
    5. func 在同步內執行呼叫端傳入的 callback 時，註解必須寫明這一點，以及 callback 執行期間哪些呼叫會等待，例如「`loader` 在同步內執行。同一個 `key` 的其他呼叫會等到它結束」。callback 有限制時也必須寫明，例如，物件的所有 func 都會取得同一把鎖時，callback 嚴禁呼叫該物件的任何 func，包括目前執行中的 func。Go 的 `sync.Mutex` 不可重入，在 `Unlock` 之前再次 `Lock` 會永遠阻塞。
5. 歷史資訊隔離：修改的歷史只記於 commit message，嚴禁寫入程式碼註解。
6. 同次補齊：進行變更時，受影響的程式碼缺少必要註解，或註解與已確認的用途、資料含意或契約不符，或不符合註解原則時，必須在同次變更中補齊或修正。

## log 原則

1. 資訊用途：每一個資訊必須有其追溯的意義，可於事後追蹤、統計、分析或除錯。對上述行為毫無幫助的資訊嚴禁寫入 log。
2. 來源位置：每一條 log 必須能追溯到唯一的程式碼位置，由訊息本身的唯一性或 logger 自動附加的來源位置來識別。
3. log 格式：log 必須採精簡結構，嚴禁文章式描述。有專案結構化欄位慣例時必須沿用；否則採固定順序的位置式格式。欄位含意由程式碼位置定義。
4. 統計聚合：只為統計而寫的 log 必須預先聚合，再定時或定次輸出，而非逐筆寫入事件。
    1. 若無法容許遺失尚未輸出的區間資料，則逐筆記錄，並允許由這些 log 事後統計。
    2. 已因診斷或稽核需求保留的事件 log，可重用於統計。
5. 記錄層級：若專案沒有 level 政策，`DEBUG` 用於除錯、`INFO` 記錄有意義的生命週期事件與聚合統計、`WARN` 記錄可恢復的降級、`ERROR` 記錄需要人處理的失敗結果。
6. 內容限制：嚴禁傾倒整個 request、response 或物件。記錄這些資料中的欄位時，payload 大小與欄位數量依專案上限。無上限時，只記錄可協助排查問題的必要欄位。

## 執行覺察

1. 符號工具：處理程式碼或 HTML 時，若目前環境提供可用且支援該語言的 `LSP` 工具，必須優先使用，讓查找與修改依照真正的程式 symbol；否則以文字工具處理。
2. 色彩空間：網頁與 CSS 的顏色必須以 `OKLCH` 定義。其他視覺輸出以 OKLCH 挑色，再轉換為目標格式支援的色彩空間。
