# Code Rules

- 規範的優先順序必須為：專案明文規範、現有專案程式碼中一致的慣例、語言慣例，最後才是以下規則。以下規則沒有決定的設計取捨使用 `arch-rules`。
- 以下規則與語言無關；例子使用 Go，必須依目標語言調整語法與型別。

## 變更原則

1. 改變行為前，必須先讀直接 caller、覆蓋受影響行為的測試與所在模組，確認現有契約。

## 程式碼原則

1. 巢狀限制：控制結構最多 2 層，`if`、迴圈、`switch` 與例外處理區塊各算一層，例如 Go 的 `if`、`for`、`switch`、`select`。
    1. `if a { for _, x := range xs { use(x) } }` 允許，在其中再加第三層結構，例如 `if b`，則禁止。
    2. `if` / `else if` / `else` 串接算一層；`try` 與其 `catch`、`finally` 區塊也算一層。
2. 函式內容：同一個目的的一組步驟，必須抽出為函式，以命名表達該組目的；只有當命名能明確包含多行程式碼組合起來的含意時才抽出。
3. 函式聚攏：若多個函式的涵義可以進一步以內聚力更高、含意邊界更清晰的名稱匯集起來，就該建立型別或模組收攏這些具有相同 scope 的函式，例如 Go 的 package 或帶有 method 的型別。
4. 函式參數：非建構子的邏輯函式參數最多 3 個，在可預見的未來必須維持簽名的穩定性。
    1. 超過 3 個意味著該函式可能有過多的責任：把多個各自有含意的計算寫在同一個函式，這些計算就只能一起執行，無法單獨使用。必須先審視能否依責任拆成多個函式；參數屬於相同 scope 時，才使用新的型別來包裝，此舉也滿足下面的穩定性原則。
    2. 若函式在可預見的未來會有持續擴充參數的可能，則必須使用特定的型別包裝相同 scope 的參數，避免簽名破壞性更新，並且必須註明清楚每個參數是否必填或預設值是什麼。
    3. 執行脈絡與接收物件不計入上限，例如 Go 的 `context.Context` 與 method 的 receiver。
    4. 受框架或函式庫約束的函式簽名不受參數上限限制，仍必須遵守外部契約。
5. 函式行數：維持 50 行內，行數從函式簽名的第一行算到結尾的那一行，包含空白行與註解；若必定超過則參考第 2、3 項調整。若內容類似「多個 `if-else` 串接」、「逐一判斷多種錯誤」這種機械式操作，則意味著結構設計問題，必須以更高層面的角度設計來避免。
6. 相同涵義常數：若有許多地方的常數都代表同一個含意，必須使用一個常數來指定或串接，以明確的程式碼代表它們的關聯。
    1. 例如 URL 路徑前綴，一個 scope 的 API 端點的前綴定義一個常數串接；嚴禁以字面值重複寫出前綴，讓更換前綴時只需改一個常數，也更方便追蹤。
    2. 測試必須獨立指定請求與預期結果中的待驗證值，嚴禁引用正式程式中定義該值的常數，讓常數寫錯時測試會失敗。多個測試指定同一含意的值時，必須使用測試專用常數。只在一個測試指定的值寫成字面值。這是相同涵義常數共用原則的唯一例外。
7. 型別命名必須表達資料的含意或職責。後綴必須補充具體含意，例如 `ShippingConfig` 表示配送設定。嚴禁使用未增加含意的後綴，例如無法與 `Member` 區分的 `MemberData`。
8. 呼叫順序：函式之間允許有呼叫順序，也就是必須先呼叫某個函式，另一個函式才能正確執行，例如先 `index.Load()` 才能 `index.Find(key)`；但呼叫順序嚴禁隱含，必須以註解說明，見註解原則第 3 項。
    1. 未依順序呼叫的函式必須以註明的錯誤失敗，並包含明確的錯誤訊息，例如 Go 回傳 `ErrNotLoaded`。
    2. 呼叫順序也可以改由型別表達，由編譯器檢查，此時不需要註解說明與前一個子項：先呼叫的函式回傳下一步使用的物件，例如先以 `connection, err := gateway.Connect()` 取得連線，再呼叫 `connection.Send(message)`；沒有連線就無法呼叫 `Send`。
    3. 必須有明確的理由，才能設計成有呼叫順序的限制；例如 `Connect()` 必須先執行一次才能呼叫其他函式，但它的成本可能很高，所以由呼叫端決定在建立時呼叫，還是延後到第一次使用時才呼叫。
    4. 釋放資源的函式不在此限：型別必須遵循語言釋放資源的慣例，由持有它的程式釋放；例如 Go 的型別實作 `io.Closer`，只在一個函式內使用該物件時，以 `defer` 關閉。
    5. 測試框架保證的呼叫順序不在此限，例如 Go 的 `testing` 在測試結束後呼叫以 `t.Cleanup` 註冊的函式。
9. override：override 已有實作的 method 時，行為必須與被 override 的 method 不同；沒有不同時嚴禁 override。在 Go，本項適用於外層型別宣告的 method 與嵌入型別提升的 method 同名的情況。
10. 執行緒安全：型別預設為非執行緒安全；需要執行緒安全的型別必須以註解寫明，見註解原則第 4 項。這裡的執行緒是指語言並行執行的單位，例如 Go 的 goroutine。
    1. 設計給單一執行緒使用的型別不需要同步，避免沒有必要的效能成本，例如每次產生報表建立一個的 builder。
    2. 設計給多個執行緒共用的型別，可以在型別內部完成同步，例如 Go 在型別內宣告一個 `sync.Mutex` 的 field，讓呼叫端不需要同步就能安全使用；同步會讓呼叫端等待時，必須以註解說明等待的行為。
    3. 在型別內部同步時，必須一起完成的多個步驟必須提供成一個 method，例如「不存在才寫入」提供 `StoreIfAbsent(key, value)`，嚴禁讓呼叫端先呼叫 `Contains(key)` 再呼叫 `Store(key, value)`；每個 method 各自同步，不代表連續呼叫也安全。使用其他執行緒安全的物件時也一樣，必須呼叫它提供的單一 method，例如 Go 呼叫 `sync.Map` 的 `LoadOrStore(key, value)`，嚴禁先呼叫 `Load(key)` 再呼叫 `Store(key, value)`。
    4. 必須一起完成的步驟中，有只能由呼叫端決定的邏輯時，必須以 callback 提供該邏輯，並在同一次同步內執行，例如 `cache.GetOrLoad(key, loader)` 只在 `key` 不存在時呼叫 `loader` 並寫入它的結果；必須以註解說明 callback 在同步內執行。
    5. interface 定義的邏輯必須是執行緒安全時，每個實作都必須是執行緒安全；實作可以有執行緒安全與非執行緒安全兩種時，由各實作自行決定。屬於這兩種情況之一時，必須在 interface 的註解寫明；不屬於這兩種情況的 interface 不需要寫，與型別的預設相同。
    6. method 的執行緒安全必須與它所屬的型別相同；嚴禁執行緒安全的型別有不能同時呼叫的 method，若出現這種情境通常意味著責任不清的問題，必須調整。

## 錯誤原則

1. 禁止隱藏失敗：嚴禁吞掉錯誤、回傳假成功，或在契約未定義 fallback 時靜默降級。
2. 處理位置：只在能恢復、能轉換為邊界契約、或能決定最終結果的地方處理錯誤；其他地方必須讓錯誤傳遞給上層，需要附加上下文時，傳遞保留原本錯誤的新錯誤，例如 Go 的 `fmt.Errorf("load orders: %w", err)`。
3. 單次記錄：同一個失敗只 log 一次，由決定最終結果的那一層負責。嚴禁每層都 log 又往上傳。

## 架構原則

1. 組合代替繼承：多個型別有相同 scope 的一組欄位或行為時，必須以獨立的型別組合而非繼承，透過 interface 定義共同契約。
    1. 例如 API 的 request/response 通常會利用父類來收斂相同的欄位，但相同欄位可能還是有 scope 區分，透過組合與 interface 定義可以合適的區分 scope 使 API 的 request/response 擁有必要且沒有多餘的內容。
    2. 除非是必要繼承則不在此限，例如語言的例外型別、lib 要求需要繼承才能執行的情況。但 lib 的情況可以考慮使用 adapter 來轉接組合以滿足此原則。
2. 模組邊界：每個模組必須以自己定義的 input/output 型別作為對外邊界；模組外部只能透過該邊界使用模組，嚴禁相依模組的內部實作。
    1. 例如業務邏輯不相依溝通協定：HTTP 的 request/response，例如 Go 的 `*http.Request` 與 `http.ResponseWriter`，必須透過一個 adapter 轉換為業務模組邊界的 input/output 型別，這樣才能解耦業務邏輯與溝通協定。框架綁定的請求參數也必須先轉成模組邊界的輸入型別再呼叫模組，該進入點嚴禁包含業務邏輯。
    2. 邊界傳入的參數一律進行驗證，在同一模組信任範圍內，嚴禁逐層機械地重複相同驗證。
    3. 驗證只拒絕契約不允許的值；`0`、`false` 與空字串並非一律無效。
    4. 契約允許省略的值必須寫明預設值。若省略與明確傳入零值，例如 `0`、`false` 或空字串，有不同含意，輸入型別必須能區分兩者，例如 Go 的欄位宣告為 `*int` 而非 `int`，以 `nil` 表示省略。
    5. 新增必填輸入（個別參數或輸入型別的欄位），或將既有輸入改為必填前，必須檢查資料的建立與載入來源，找出會缺值的來源，並確認邊界的驗證能識別缺值；可控制的來源在同次變更更新，無法同步更新的來源，保留相容入口，或明述不相容變更與遷移方式。例如 `MemberRegistration` 新增必填欄位 `Locale` 時，已儲存的舊資料與其他建立會員的流程沒有這個值。
    6. 重組內部實作時，必須維持對外操作的呼叫方式與呼叫端責任，既有輸入含意、結果與錯誤也必須維持。
3. 功能解耦：跨模組邊界的功能，或實作尚未定案、需要替換的功能，必須透過 interface 隔離提供實作，並確立好該 interface 的所有 input/output 是否足夠獨立，僅相依必要的其他模組元件。模組間若邊界無關連則透過 adapter 耦合，避免依賴。
4. 禁止循環相依：模組之間的相依嚴禁直接或間接形成循環。循環相依意味著模組功能模糊，必定能再抽出更底層的邏輯將循環相依拆開。
5. 邏輯分支：已知需求或既有擴充點顯示 `if-else`/`switch` 的分支會持續增加，且每個分支對應一組獨立邏輯時，必須讓選擇分支的責任與處理邏輯解耦，使其可以獨立發展；嚴禁只因分支增加就把 `switch` 換成 `map` 或 Strategy。
    1. 封閉集合：選擇分支的模組擁有全部分支，新增分支時允許修改選擇者。保留 `switch`，每個分支呼叫一個具名的函式。
    2. 開放集合：分支由其他模組或在執行時提供，新增分支時不得修改選擇者。以唯一的 key 選擇分支時，必須使用分派表：由外部註冊 key 與處理者的對應，選擇者只相依共同的 interface。
    3. Strategy Pattern 是處理邏輯的封裝方式，可與上述兩種選擇方式並用：各分支有各自的設定與邏輯，且需要以共同的契約替換時使用；固定且簡單的分支嚴禁只為套用模式而建立 Strategy。
6. 資料與邏輯分開：資料型別，也就是只用來承載資料的型別，例如 DTO、API 的 request/response，只宣告欄位與存取欄位的函式，嚴禁帶有任何邏輯；邏輯必須放在使用這些資料的函式或型別。邏輯是指依欄位值做判斷、計算或轉換，或讀取外部狀態的程式。
    1. 例如判斷查詢點是否位於搜尋範圍內，必須寫成函式 `func Contains(bounds Bounds, x, y float64) bool`，嚴禁寫成 `Bounds` 的 method `func (bounds Bounds) Contains(x, y float64) bool`。
    2. 建構時的驗證也屬於邏輯，嚴禁寫在資料型別內；資料由接收它的邊界驗證，見本章節第 2 項。
    3. 預設值的替換與格式的正規化，例如去除前後空白，也屬於邏輯，嚴禁寫在資料型別內。契約定義的預設值由定義該契約的邊界替換；正規化可以由邊界處理，也可以由呼叫端在傳入前處理，例如同一筆資料要傳給多個模組時只處理一次。
    4. 由邊界替換預設值或正規化，且邊界是 interface 並有多個實作時，必須寫在各實作共用的一個函式，嚴禁每個實作各寫一份；例如 `MemberSearch` 的每個實作都呼叫 `ApplyMemberQueryDefaults(query)`。
    5. 為了讓來源集合之後的修改不影響資料而複製集合不屬於邏輯，例如 Go 在建立該值的函式以 `slices.Clone` 複製 slice。
    6. 列舉型別也適用本項：每個值可以有與值一起宣告的固定屬性，並提供只查出並回傳該屬性的 method，例如 Go 的 `func (channel Channel) MaxLength() int` 由以常數為索引的表回傳長度上限；依屬性或傳入的參數做判斷或計算的 method 屬於邏輯，嚴禁寫在列舉型別內，例如 `func (channel Channel) Accepts(text string) bool`。由固定屬性找出對應值的函式不屬於邏輯，例如 `func ParseChannel(code string) (Channel, error)`。
    7. 語言有專門宣告純資料的型別時，例如 Java 的 `record`，列舉型別以外的資料型別必須使用它宣告，並採用欄位在建構後無法改變的形式；只有語言版本或函式庫不支援該宣告時才改用其他方式宣告，例如函式庫要求無參數建構子與 setter。帶有邏輯的型別嚴禁使用它宣告，例如 Strategy 的實作。

## 註解原則

1. 高階意圖：僅描述高階用途、資料含意、契約、限制與取捨。嚴禁逐步描述實作。
2. 清單結構：註解有兩個以上獨立要點時，必須用清單結構，而非文章式的描述。
3. 用途註解：每個型別、函式與 field 都必須有精簡註解，提供用途或含意的高階概覽。
    1. 型別的註解必須說明職責與範圍。優先描述所負責的功能；不負責的功能由流程或模組邊界表達。
    2. field 的註解必須說明資料含意，若有固定格式則必須提供範例。
    3. 函式的任一參數有名稱與型別看不出的含意、格式、單位、可否不提供（例如 Go 的 `nil`），或省略時的預設值時，必須依語言的文件慣例在函式的註解說明每一個參數，例如 Javadoc 的 `@param`；Go 沒有參數標記，把每個參數寫成 doc comment 內的清單項目；若有固定格式則必須提供範例；所有參數都能由名稱與型別看出時，省略全部的參數說明。
    4. 實作 interface 的 method 或 abstract method 時，契約已由被實作的 method 說明，註解只寫這個實作特有的行為與限制。沒有時，宣告已標示被實作的 method 就不需要註解，例如 Java 的 `@Override`；否則寫一行指出它實作的型別，例如隱含滿足 interface 的 Go 寫 `// Send 實作 Sender。`
    5. override 已有實作的 method 時，註解必須說明它與被 override 的 method 不同的行為，見程式碼原則第 9 項。
    6. 函式若有型別與簽名無法表達的前置條件必須明確列出，例如呼叫端必須已完成的驗證、跨模組契約，以及呼叫順序（見程式碼原則第 8 項）；無此類限制時省略這些補充項目。呼叫順序必須註明必須先呼叫哪一個函式，以及未依順序呼叫時回報的錯誤；只能呼叫一次的函式必須註明這個限制，以及重複呼叫時的行為。嚴禁只為重述呼叫關係而列出 caller 或 callee。
4. 執行緒安全：型別註解沒有說明就代表非執行緒安全，也就是同一個實例嚴禁由多個執行緒同時使用；執行緒安全的型別必須在型別註解寫明，用語依語言的慣例，例如 Go 的「可由多個 goroutine 同時使用」。
    1. 持有的資料在建構後不會改變的型別本來就是執行緒安全，不需要寫明，例如列舉型別、Java 的 `record`。是否會改變必須依實際的程式碼判斷，嚴禁只看宣告，例如 Go 以值傳遞 struct 時會複製，但複本的 slice field 仍與原本的值共用元素。
    2. 其他型別設計為執行緒安全時必須寫明，例如 Go 以 `sync.Map` 保存資料、由多個 goroutine 共用的 cache，註解寫「可由多個 goroutine 同時使用」。
    3. interface 定義的邏輯必須是執行緒安全時，interface 註解必須寫明，例如「實作必須可由多個 goroutine 同時使用」；實作可以有執行緒安全與非執行緒安全兩種時也必須寫明，例如「實作是否可由多個 goroutine 同時使用，依各實作的註解」。不屬於這兩種情況的 interface 不需要寫；沒有寫明時，嚴禁假設它的實作是執行緒安全。
    4. 同步會讓呼叫端等待時，註解必須寫明哪些 method 會互相等待，例如「可由多個 goroutine 同時使用：`Reload` 執行期間，其他 method 的呼叫會等到它結束」；等待可能很久時，還必須寫明原因，例如持有鎖期間讀取檔案。
    5. method 在同步內執行呼叫端傳入的 callback 時，註解必須寫明這一點，以及 callback 執行期間哪些呼叫會等待，例如「`loader` 在同步內執行；執行期間，同一個 `key` 的其他呼叫會等到它結束」；callback 有限制時也必須寫明，例如嚴禁在其中呼叫同一個物件的 method，因為 Go 的 `sync.Mutex` 不可重入：在 `Unlock` 之前再次 `Lock` 會永遠阻塞。
5. 歷史資訊隔離：修改的歷史只記於 commit message，嚴禁寫入程式碼註解。
6. 同次補齊：進行變更時，受影響的程式碼缺少必要註解，或註解與已確認的用途、資料含意或契約不符，或不符合註解原則時，必須在同次變更中補齊或修正。

## log 原則

1. 每一個資訊必須有其追溯的意義，可於事後追蹤、統計、分析或除錯。對上述行為毫無幫助的資訊嚴禁寫入 log。
2. 每一條 log 必須能追溯到唯一的程式碼位置：訊息本身唯一，或 logger 自動附加來源位置皆可。
3. log 必須採精簡結構，嚴禁文章式描述。有專案結構化欄位慣例時必須沿用；否則採固定順序的位置式格式。欄位含意由程式碼位置定義。
4. 只為統計而寫的 log 必須預先聚合，再定時或定次輸出，而非逐筆寫入事件。
    1. 若無法容許遺失尚未輸出的區間資料，則逐筆記錄，並允許由這些 log 事後統計。
    2. 已因診斷或稽核需求保留的事件 log，可重用於統計。
5. 若專案沒有 level 政策：`DEBUG` 用於除錯、`INFO` 記錄有意義的生命週期事件與聚合統計、`WARN` 記錄可恢復的降級、`ERROR` 記錄需要人處理的失敗結果。
6. 嚴禁傾倒整個 request、response 或物件。payload 大小與欄位數量依專案上限；無上限時只記錄選定欄位。

## 執行覺察

1. 處理程式碼或 HTML 時，若目前環境提供可用且支援該語言的 `LSP` 工具，必須優先使用，讓查找與修改依照真正的程式 symbol；否則以文字工具處理。
2. 網頁與 CSS 的顏色必須以 `OKLCH` 定義。其他視覺輸出以 OKLCH 挑色，再轉換為目標格式支援的色彩空間。

1. 參數數量：函式現有或規劃中的簽名超過 3 個參數時，必須先讀[參數數量範例](references/parameter-examples_ch.md)，再決定如何拆分職責或包裝參數。
2. 分支選擇：已知需求或擴充點顯示 `if-else`/`switch` 的分支會持續增加，且每個分支對應一組獨立邏輯時，必須先讀[分支選擇範例](references/branching-examples_ch.md)，再決定是否使用分派表或 Strategy Pattern。
3. 宣告註解：撰寫或修改程式碼前，必須讀[宣告註解範例](references/comment-examples_ch.md)，並遵循註解原則與範例示範的註解方式。
4. log：撰寫或修改 log 前，必須讀[log 範例](references/logging-examples_ch.md)，並遵循 log 原則與範例示範的寫法。
