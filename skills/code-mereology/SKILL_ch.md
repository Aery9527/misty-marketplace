# Code Mereology

設計文件負責定義模組邊界與行為；實作細節只存在於程式碼中。設計文件經確認後轉成
具體的 SBE 範例，範例直接寫成失敗的測試，再由這些測試驅動程式碼誕生。測試是規格
唯一的家，嚴禁把規格重複寫進文件。`sd-*-plan.md` 是一份用完即丟的未來工作意圖，
不是另一個規格來源。

## 階段路由

- 若任務只要求記下或檢視延後的 plan，不進入任何 phase。依照[延後變更計畫](#延後變更計畫)執行，且嚴禁載入 phase reference。
- 若使用者選擇執行某一筆延後變更條目，只把那筆條目視為 feature request，再依下方規則選擇 phase。該條目嚴禁跳過設計或測試的確認 gate。
- 若任務是建立或修改設計文件，或是把功能拆分成模組，載入 [Phase 1 — 模組化設計](references/phase1-design_ch.md)。
- 若已有經確認的 leaf 設計文件，且任務是定義具體 input/output 範例、挖掘 edge case，或把它們落成失敗的測試，載入 [Phase 2 — SBE 落成失敗測試](references/phase2-sbe_ch.md)。
- 若已有一組經確認的失敗測試，且任務是對著它做實作，載入 [Phase 3 — 實作](references/phase3-tdd_ch.md)。
- 若功能已實作完成，且任務是量測吞吐、延遲或資源消耗，載入 [Phase 4 — 效能驗證](references/phase4-benchmark_ch.md)。
- 其餘情況代表這是一項還沒有既有產出可接續的功能或模組變更，載入 [Phase 1 — 模組化設計](references/phase1-design_ch.md)。必須先比對上面四條；這一條只接住四條都沒接住的任務。
- 四個階段各自可獨立載入，必須依當前任務只載入需要的階段，嚴禁載入當前任務不需要的階段 reference。
- 以上五條 phase 規則是唯一的 phase reference 載入判斷依據，且必須依序比對。每份 reference 都寫明自己的產出物；依賴前一階段產出的那幾個階段，另外寫明動手之前必須驗證的狀態，因此任一階段都能在冷載入的情況下獨立執行。

## 文件模型

文件分兩層下降：描述「組裝起來的整體」的主題層，以及描述「組成它的組件」的模組層。

- `bd-<主題名稱>.md` — 組裝文件，放在 scope 根目錄下的 `docs/` 中——repository 根目錄，或 monorepo 中的 submodule 根目錄。主題可以是一項業務需求、一段架構說明或一條端到端的 data flow。Mermaid 圖必須呈現結構角色及其關係規則。標頭的 `parts` 必須列出文件圖中的下一層實際節點。詳見[組裝文件撰寫規則](references/phase1-design_ch.md#撰寫規則--組裝文件)。不受行數上限限制，且嚴禁下沉到下層設計文件已負責的行為細節。
- `sd-<功能名稱>.md` — 設計文件。它的主題是單一模組——組裝整體所用的一個組件。必須放在對應程式碼所在的資料夾，嚴禁集中收納到 `docs/`。`<功能名稱>` 嚴禁以 `-perf` 或 `-plan` 結尾，藉此區分設計文件與它旁邊的暫存紀錄。
- `sd-<功能名稱>-plan.md` — 放在既有 `sd-<功能名稱>.md` 旁邊的暫存延後變更計畫。它描述預計日後執行的工作，不是規格也不是文件圖節點，可以完全不被其他文件連結。它靠 plan search 被發現，不靠文件圖走訪。它不受行數上限限制，因為那條上限衡量的是設計的認知負擔，而 plan 是延後的意圖，不是設計。
- `sd-<功能名稱>-perf.md` — Phase 4 寫在被量測程式碼旁邊的效能紀錄。它記錄的是某次量測到的事實，而不是系統如何組裝，因此不屬於下方那張圖，任何階段都不會走進它。它不受行數上限限制，因為那條上限衡量的是設計的認知負擔，而它是量測結果的紀錄。
- 兩層回答的是不同問題：`bd-*.md` 回答這個系統交付什麼、各部分如何組合起來交付它；`sd-*.md` 回答單一部分做什麼、它的邊界在哪。讀者從主題進入，再往下走到組件。

在模組層內部，`sd-*.md` 本身還可以再形成一棵樹，每個節點擔任以下兩種角色之一：

- overview 角色 — 描述抽象概念，並連結到下層子模組的設計文件。嚴禁作為 Phase 2 的輸入。
- leaf 角色 — 描述單一模組自身的行為，並連結到目標程式碼。只有 leaf 才是 Phase 2 的合法輸入。

已經實作且沒有設計文件的模組，有新功能依賴它時，可以先以 partial leaf 進場。它只描述目前需要的能力。Partial 是 leaf 的屬性。必須用 `code-mereology-partial` 標記列出已涵蓋的能力。Phase 2 嚴禁用它為未涵蓋的能力定規格。移除標記或升格為 overview 時，必須在同一次 Phase 1 沿 `parts` 接到適當的組裝主題。若沒有適當主題，必須請使用者確認一份只涵蓋本次轉換的新主題。見 [partial leaf](references/phase1-design_ch.md#partial-leaf)。

### 文件關係

- `parts` 列出文件主題的組成。
    - 跨 submodule 主題由 repository root 的組裝文件連到參與的 submodule 組裝文件，再經由各組裝文件到達其模組。Submodule 組裝文件的責任必須限於自己的 scope。
    - 組裝文件連到同一 scope 內參與的模組文件。Overview 連到子模組文件。
    - Leaf 將程式碼介面連結留在正文。這些連結不屬於文件關係圖。
- `depends` 列出主題需要外部提供的能力或結果。
    - Leaf 可跨 scope 依賴其他 leaf。Partial leaf 可以被依賴，其自身 `parts` 與 `depends` 必須留空。有 `parts` 的模組文件嚴禁宣告依賴，也嚴禁成為依賴目標。
    - 組裝文件的依賴表示需要另一個主題交付的結果。Root 層的組裝文件可互相依賴。同為 submodule 層的組裝文件可跨目錄依賴。Root 與 submodule 組裝文件嚴禁用 `depends` 相連。
- 每份一般 `sd-*.md` 必須能從組裝文件沿 `parts` 到達。每份 partial leaf 必須有來自另一份文件的 `parts` 或 `depends`。規劃中的邊不算到達。`parts` 成環是錯誤。依賴環是否保留由使用者在 Phase 1 決定。
- Phase 1 核對文件角色和組裝文件的抽象層級。腳本驗證依賴兩端的檔案種類，也拒絕涉及有 `parts` 的模組文件的依賴。

### 標頭與 tag

- H1 用 `# `，之前可有 frontmatter 與空行。H1 到第一個 `## ` 標題或檔尾之間只含空行、緊接 H1 的選用 partial 標記，以及標頭區塊。區塊必須依序包含 `parts`、`depends`、`tags`，各出現一次。無值的鍵留空。
- 每個 `parts` 或 `depends` 項目必須有一個 Markdown inline link，並在 `: ` 後寫一行說明，嚴禁包含 tab。`parts` 說明目標扮演的角色，`depends` 說明所需能力或結果。規劃中的文件還不存在時，在連結與冒號間加 `(planned)`。文件存在後移除標記。
- 關係連結必須是單行且沒有 title。Label 嚴禁包含方括號，目標嚴禁包含空白或括號。
- 區塊內的 link label 必須唯一。同一來源、關係型別及目標只宣告一次。目標使用相對於來源且大小寫正確的正斜線路徑。目標必須在掃描範圍內，嚴禁絕對路徑、查詢字串及 fragment。
- 指向本 repo 另一份設計或組裝文件的連結必須在標頭使用其檔案路徑。正文嚴禁連到該檔案或其 fragment，改用字面完全相同的 `*label*` 提及該文件。斜體專用於這些提及，其他強調用粗體。嚴禁用底線表示斜體或對 label 疊加粗體。正文可保留程式碼、同檔標題、外部連結及 `-plan` 或 `-perf` 連結。
- 宣告的 tag 寫成 `tags` 行上以逗號分隔的 inline code。文件沿 `parts` 繼承各上層宣告的 tag，有多個上層時取聯集。Tag 宣告在適用範圍最上層，嚴禁重複宣告已繼承的 tag。`depends` 和規劃中的邊不傳遞 tag。
- 每個 repository 根目錄只用一份 `docs/code-mereology.json`，monorepo 也一樣。選用的 `tags` 物件將名稱對應到描述。名稱是以連字號分隔的一到三段小寫英文字母或數字。每個宣告的 tag 必須在表中，表中的每個 tag 必須至少由一份受掃描文件宣告。選用的 `exclude` 清單列出已存在且相對於 root 的目錄，大小寫必須正確並使用正斜線。腳本略過這些目錄及其子樹。設定檔不存在時，tag 表與排除清單視為空。
- 設定檔只可使用 `tags` 與 `exclude` 兩個鍵。排除路徑嚴禁包含 `..` 或經過目錄連結。掃描也略過版本控制目錄、`.worktree` 與目錄連結。

```text
# 主題

- `parts`:
    - [模組](../module/sd-module.md): 提供主題所需的模組能力
- `depends`:
- `tags`: `backend`
```

### 查詢與啟用

```text
node <skill-root>/scripts/list-relations.mjs [-a <文件> [-f <關係>] [-d <深度>]] [-t <tag>] <repository-root>
```

- 從已載入的 skill 目錄推導腳本路徑。流程內查詢必須明確傳入整個 repository 的根目錄。`-a` 的文件相對於目前目錄。`-f` 可組合 `p` 上層、`c` 下層、`d` 依賴目標和 `u` 依賴者，預設 `pcdu`。`-d` 接受正整數，預設 `1`，用 `a` 表示不限深度。
- `-t` 依有效 tag 列出候選文件。用 `-a` 查候選文件的關係。兩個選項都省略時，輸出全部宣告的關係與 tag。嚴禁同時使用 `-a` 與 `-t`。
- 輸出為 TSV。邊的欄位依序是來源、`parts` 或 `depends`、目標、說明、選用的 `planned`。反向查詢保留原來源與目標。Tag 欄位依序是文件、`tag`、名稱、選用的 `inherited`。
- 有查詢選項時，腳本仍驗證掃描範圍內所有文件。文件或設定檔錯誤回傳 `1`，參數錯誤回傳 `2`，驗證通過回傳 `0`。
- 採用本流程前，從實際 repository root 執行沒有查詢選項的 [list-relations.mjs](scripts/list-relations.mjs) 並確認通過。有缺少標頭的文件時，停止並列出檔案，讓使用者決定是否遷移。遷移後再查。與原始文件重複的生成副本必須排除。
- 影響查詢必須回傳 `0`，才可把 stdout 當成完整結果。非零時，stdout 只供診斷。先修正本次編輯造成的錯誤再重跑。遇到任務範圍外的錯誤，或在階段之外發現既有錯誤，必須停止並回報。Phase 1 依既有 gate 修正範圍內錯誤。Phase 3 發現範圍內的既有圖錯誤時，退回 Phase 1。Phase 3 依程式碼修正既有 partial leaf 契約的例外仍適用。

## 延後變更計畫

- 只有當使用者要把某個模組變更留待日後執行時，才在既有 `sd-<功能名稱>.md` 旁建立 `sd-<功能名稱>-plan.md`。移除 `-plan` suffix 後，basename 必須與對應設計文件完全相同。
- `sd-<功能名稱>-plan.md` 可以裝下不只一筆延後變更條目。一份已交付的設計文件會隨著時間陸續收到新的變更需求，每一項都可以在輪到執行之前先被記下。條目之間要用一行空白、一行獨立的 `---`、再一行空白隔開——前後的空白行是必要的，因為緊接在一段文字下面的 `---` 會被解讀成標題底線，而不是分隔線。檔案開頭嚴禁以 `---` 起始，那在檔案最上方會被讀成 frontmatter 分隔線，而不是條目分隔線。條目必須依記錄先後附加在檔案後面，且每筆都必須自成一體：內容嚴禁依賴讀懂同一份檔案裡的另一筆條目。
- 每筆條目開頭必須先寫下它存在的原因——促成這項變更的需求或觀察——再寫 delta 本身。等到當時的情境從記憶中淡去，這個原因才是讓後續讀者判斷這筆條目是否還值得執行的依據。除了原因之外，條目必須只記錄預計發生的 delta，以及日後恢復工作所需的執行、migration 或驗證資訊。嚴禁把提案行為寫成現在的事實或已確認規格。Phase 1 必須重新驗證提案行為，Phase 2 必須重新驗證其中的具體範例。
- Plan 檔案可以完全不被其他文件連結。組裝與設計文件嚴禁只為了讓 plan 檔案可被找到就增加一條指向它的結構邊；plan 檔案本身可以為了提供 context 而往外連到現行設計或程式碼。
- 延後變更條目可以延後任意時間。檢視尚未執行的 plan 時，對 repository root 執行 [list-plans.mjs](scripts/list-plans.mjs)，再讀取每一份回報的文件，摘要它裡面每一筆條目尚未完成的工作。
- 任何 phase 選定或走訪一份 `sd-<功能名稱>.md` 時，都必須推導同目錄的 `sd-<功能名稱>-plan.md` 路徑，並在檔案存在時讀取。這項 filename lookup 讓冷載入仍能發現 plan 檔案，不需要把它加入文件圖。
- 使用者選定要執行某一筆條目時，只把那筆條目當成 feature request；同一份檔案裡的其他條目維持延後。Phase 1 必須先更新並確認對應的設計文件。Phase 2 把 SBE 凍結成失敗測試、Phase 3 完成實作之前都保留該條目。條目讓意圖可以跨越暫停，但永遠不能取代任何 phase 要求的產出物。
- 某筆條目描述的工作交付、且必要測試全綠後，必須驗證對應的 `sd-<功能名稱>.md`，以及所有受影響的組裝、上層與依賴者文件都已描述交付後的行為。驗證完成後，在同一個 change 裡刪除那筆條目；若檔案裡還留有其他條目，每一對相鄰條目之間必須剛好保留一組「空白行、---、空白行」分隔。只有當檔案裡不再留下任何條目時，才刪除整份檔案。嚴禁刪除未完成的條目；檔案不存在就表示該設計文件沒有延後工作留下。
- `-plan.md` suffix 與 `(planned)` link marker 互不相關。[list-plans.mjs](scripts/list-plans.mjs) 用來發現延後變更文件；[list-planned.mjs](scripts/list-planned.mjs) 用來發現設計文件裡尚未實現的目標承諾。

一份 `sd-<功能名稱>-plan.md` 裡有兩筆條目時，看起來像這樣：

```markdown
Why: <促成這筆條目的需求或觀察>

<預計發生的 delta，以及日後恢復工作所需的執行、migration 或驗證資訊>

---

Why: <促成下一筆條目的原因>

<它自己的 delta 與備註>
```

執行搜尋腳本時，必須從安裝後的 skill root 推導路徑，嚴禁假設固定安裝位置：

```bash
node <skill-root>/scripts/list-plans.mjs <repository-root>
```

## 跨階段規則

- 設計文件嚴禁出現程式碼。介面與 data view 必須以 Markdown link 指向目標程式碼，因為重複記載的細節終將與它所描述的程式碼脫節。
- 設計文件必須描述行為與注意事項。嚴禁重複演算法、控制流程或欄位層級的結構；只有當某個實作選擇實質定義了模組邊界、對外可觀察行為或相容性契約時，才可以指名該實作。
- 只要文件能把關係、data flow 或狀態轉換畫成圖，就必須使用 Mermaid。
- Mermaid 區塊必須使用剛好三個反引號與小寫的 `mermaid` 標記，嚴禁附加其他圍欄屬性，且必須從第一欄開始、前面不得有任何空白。嚴禁使用四個反引號圍欄、波浪號圍欄，也嚴禁把圖縮排放進清單項目或引用區塊，因為行數計算依賴這個標準形式。
- 單一設計文件嚴禁超過 300 計數行；`-perf` 紀錄與 `-plan` 文件不受此限。計數行 = 檔案總行數扣除所有 `mermaid` 圍欄區塊的行數（含圍欄本身）。
- 超過 300 計數行代表該模組的認知負擔過大。往下切分子模組是唯一容許的反應。嚴禁以刪減注意事項、壓縮文字敘述或把文字搬進 Mermaid 的方式壓低行數。
- 目標尚未存在的連結，必須在其緊接之後標上 `(planned)`；目標一旦存在就必須拿掉這個標記。它必須是單行的 inline link 且嚴禁帶 title，label 內嚴禁出現方括號，destination 內嚴禁出現空白或括號。嚴禁以 reference-style link 或圖片語法表達。凡是不代表真正承諾的地方，嚴禁寫出 planned link 的形狀——不可以當成 inline code 範例，也不可以出現在圖裡——因為工具只看形狀，而它看不見的承諾會被當成已經兌現的承諾。它讓讀者分得出哪些是承諾、哪些是事實，也讓負責清除它的那個階段能用搜尋一次找齊。
    - 比對連結目的地時，空白指 Unicode `White_Space` 加上 `U+001C` 至 `U+001F`。目的地中的 `U+FEFF` 是路徑的一部分。
- 使用者必須先確認 `bd-*.md`，agent 才可往下深入它的模組；必須確認每一層 `sd-*.md`，才可往它的子層推進；並且必須在任何實作寫出來之前，確認承載凍結 SBE 的那組失敗測試。嚴禁跳過任一道 gate。
- Phase 2 與 Phase 3 是每個 leaf 各跑一輪，而不是整棵樹跑一輪。當 Phase 1 留下多個未處理的 leaf 時，由使用者決定下一個要處理哪一個。
- 標題文字由專案自行決定，但必須在該專案的文件之間保持一致：沿用同類型既有文件已經使用的標題。
- 此 skill 產出的所有設計文件都是給人類看的，因此內容盡量以 Mermaid 視覺化呈現，降低閱讀負擔。

## 階段之外的程式碼修改

不是每一次程式碼修改都循著某個階段進來。沒有循著階段進來時，同樣嚴禁讓文件停留在
描述程式碼已經不再做的事。

- 動既有程式碼之前，先看所在資料夾有沒有 `sd-*.md`。若變更影響超出該模組，執行 `-a <文件> -f pu <repository-root>`，依關係說明選出要讀的受影響文件。失敗時依[查詢與啟用](#查詢與啟用)處理。
- 修改之後，逐一拿它們對照程式碼現在的行為，把每一句已經不再成立的敘述修正掉。
- 若這次修改移動了模組邊界，或改變了呼叫方能觀察到的行為，只改文字是不夠的——那是設計變更，必須退回 Phase 1，嚴禁默默把文件改成配合剛寫出來的東西。
